# Ello Web Application

[![Build Status](https://travis-ci.org/ello/webapp.svg?branch=master)](https://travis-ci.org/ello/webapp)

The web app for [ello.co](http://ello.co).

## Running locally

The Ello API is not public, so the repo ships a mock (`mock/`, see [mock/README.md](mock/README.md)).

```bash
nvm use                      # Node 20 (see .nvmrc)
yarn install
cp .env.example .env.local   # API_ORIGIN=http://localhost:7770
yarn mock                    # terminal 1: mock API on :7770 (live: the seeded people keep posting, loving, commenting)
yarn dev                     # terminal 2: the app on http://localhost:6660
```

Log in at `/enter` as `ada@example.com` with any password of 8+ characters.

The mock is a small living network: 30 people, about 310 posts dated from the moment the database is created, background activity and a little latency while it runs. `yarn mock:static` switches the last two off (required for visual diffs), `yarn mock:reset` starts a fresh database. See [mock/README.md](mock/README.md).

| Command | |
|---|---|
| `yarn dev` / `yarn build` / `yarn start` | Next.js dev server, production build, serve the build |
| `yarn typecheck` | `tsc --noEmit` |
| `yarn lint` | ESLint (Next + TypeScript rules) |
| `yarn test` | Jest + React Testing Library |

## Stack

Next.js (App Router) · React 19 · TypeScript (strict) · Tailwind CSS 4 · TanStack Query (infinite feeds) ·
Zustand (composer draft, toasts) · React Hook Form + Zod (forms, and validation of every API response).

- Server Components read the API with the session token from an httpOnly cookie (`lib/api`, `services/`).
- Mutations are Server Actions (`actions/`); optimistic UI uses `useOptimistic`.
- Uploads go browser → storage directly with credentials from the API (`lib/client/upload.ts`).
- The previous React 15 / Redux / Webpack app is no longer in this repo. It lives on branch `feat/mock-api` (a separate checkout is needed to run it for pixel diffs). Code comments that cite `legacy/src/<path>` mean `src/<path>` on that branch.

## Design fidelity

The point of the rewrite is to keep the original design. Its tokens and base styles live in
`app/styles/` (ported from `src/styles/jso.js` and `src/lib/styles/` of the original), the icon set in
`components/icons/`, and every page was checked against the running original with a pixel diff.
Before calling UI work done, run `tools/visual-diff` (see its README): matching pages are 0.0%.

## Styling

The living style guide is at `/styleguide`: every token, the icon set, and each shared component in
its variants and states. Read it before building a page.

- **Tokens** live in `app/styles/tokens.css`: colours (`--color-*`), font stacks (`--font-*`), the
  type scale (`--text-12` ... `--text-56`), radii (`--radius-box`, `--radius-pill*`), control heights
  (`--control` 40px, `--control-small` 30px), motion (`--speed`, `--speed2`, `--ease-ello`,
  `--ease-quart`, `--ease-cubic`) and z layers (`--z-*`). Use `var(--token)` in CSS or the Tailwind
  utility (`text-gaa`, `bg-green`, `text-14`, `rounded-box`, `ease-ello`); one spacing unit is one
  pixel (`p-10` is 10px). Do not write a raw value that has a token.
- **Adding a token:** add it to `tokens.css` with a comment saying where the original has the value,
  and to `constants/design-tokens.ts`, which the style guide is drawn from.
  `constants/design-tokens.test.ts` fails when the two disagree. Only values the original uses, and
  only ones that repeat: a one-off stays a literal next to the rule that needs it.
- **Breakpoints** cannot be custom properties inside `@media`, so write them out: `(min-width: 40em)`
  bp2 640px, `60em` bp3 960px, `85em` bp4 1360px, `107.5em` bp5, `130em` bp6, `152.5em` bp7; the
  "below" queries are one pixel less (`(max-width: 39.9375em)`). Hover styles go in
  `@media (hover: hover)`.
- **Primitives** are in `components/ui/`. Reach for:

  | Need | Use |
  |---|---|
  | An action button (40px: black, green, outline, text) | `Button`, `GreenButton`, `OutlineButton`, `TextButton` (`button.tsx`) |
  | A form's submit button (60px, full width) | `FormButton`, `FormButtonSquare` |
  | The original's `RoundedRect` (artist invites) | `GreenRoundedRect`, `GreenBorderRoundedRect`, `BlackBorderRoundedRect`, `GreenXLRoundedRect` |
  | A text input with label, status icon and message | `FormControl` and its parts (`appearance`: `line`, `box`, `box-grey`, `white`); `Field` for a bare underlined one |
  | A Yes / No preference | `ToggleControl` |
  | One-of-two or pick-any choices | `OptionButton`, `CategoryOptionButton` |
  | A dialog | `Modal` + `ModalDialog`, `ModalHeading`, `ModalButton`; `ConfirmDialog` for Yes / No; `DismissButton` for its X; `dangerZone` for the red scrim |
  | A user picture | `Avatar` (responsive, or `size`) |
  | A message across the top | `toast.error()` / `toast.info()` (`stores/toast-store`), drawn by `Toaster` |
  | A single line that truncates | the utilities `max-w-full truncate` (the original's `truncate`); the usernames of every post header use them |
  | A tool of a post or comment footer, its label on hover | the global classes `PostTools` / `PostTool` (+ `ViewsTool`, `ShareTool`, `isPill` ...) of `components/posts/post-tools.css` and `Hint` (`components/posts/hint`) |
  | The follow toggle of a post header | `PostFollowButton` (streams) / `RelationshipButton` (post page): both are `.FollowButton.isInHeader` of `components/posts/post-hints.css` |
  | An editor's placeholder, region tools, drag handle, upload cover | the classes of `components/ui/editor-parts.module.css`, next to the editor's own module |
  | A hero promotion and its photo credit | `promotion` of `components/heroes/hero-promotion.module.css`; `HeroCredits`, `HeroCreditsCollapsed` (`components/heroes/hero-credits`) |
  | The column grid (2 / 3 / 4 ... columns) | the global classes `Columns` (or `Posts asGrid`) and `Column` of `components/streams/columns.css` |

- **Which rule wins.** The cascade layers are `theme, base, components, utilities` (`app/globals.css`).
  The reset and element styles are in `base`; the icons and the primitives meant to be restyled
  (`Avatar`, `ToggleControl`) are in `components`; Tailwind utilities are in `utilities`. CSS Modules
  and the few global component sheets are **unlayered**, and unlayered CSS beats every layer whatever
  its specificity. So: a page's own module always overrides a layered primitive (that is how
  onboarding turns `ToggleControl` into a big button), a Tailwind utility on an element does **not**
  override a module rule on the same property, and between two unlayered rules it is specificity,
  then source order, which across modules follows import order and should not be relied on. When a
  module must override another module, double the class (`.flex.flex`) rather than depend on order.
- **Shared pieces that are global class names** (`PostTool`, `Hint`, `FollowButton`, `Column`: the
  icons and the original's CSS key off them) have exactly one definition, in the sheet named in the
  table. A component that draws one imports that sheet itself, and a page that needs it different
  (the post page's tools, a comment's tools) writes only the declarations that differ in its module,
  at a higher specificity than the shared rule. Do not copy the shared rule into the module.
- A change to shared styles is done when `tools/visual-diff` reads the same as before on the pages
  that use them.

### Known intentional differences from the original
- **NSFW "View" button:** the original's GraphQL reducer drops `contentWarning`, so it never shows the button on feeds (`/discover`, trending, profiles...), and post detail never shows it either. The rewrite matches that: `SHOW_CONTENT_WARNING_ON_FEEDS` in `constants/content-warning.ts` is `false`, and the button (`ContentWarningButton`) still works behind it, so showing it on feeds is a one-line change. Three places do show it, because the original loads them over REST with `contentWarning` intact: an artist invite's submissions (`showContentWarning` on `PostContent`), the related posts under a post, and the posts of a search (`post-stream.tsx`).
- **Category header:** the original shows "@author in Category" (`CategoryHeader`) on the global and subscribed feeds (`/`, `/discover`, `/discover/(featured|recommended|trending|recent|shop)`, `/discover/subscribed...`) for posts that have a category. With the real API that comes from `categoryPosts` in the GraphQL stream, so the mock now returns `categoryPosts` for posts with `categoryIds` and the rewrite renders the header on the same routes (`utils/category-header-route.ts`). The original also merges the posts of its REST notification payload into its store, which could add a category header or the NSFW button to a feed post depending on when the notifications arrived; the mock's REST notifications leave `contentWarning` out so feeds do not depend on that timing.
- **Profile hero diffs:** the hero is `100vh`; pass `--vh 900` to `tools/visual-diff/vdiff.js`.
- **Shop/embeds/reposts:** see `mock/README.md` for what the mock simulates.
- **Pictures, clips and embeds in posts:** `components/posts/image-region.tsx` is the original's `ImageRegion` for streams and comments. A region is `isRequesting` until its picture has loaded (picture at opacity 0, and in a grid the box behind it cycles the placeholder colours), then the picture fades in; a picture that cannot load makes it `isFailing`, which has no styles of its own in the original either: the browser draws its broken picture. An animated upload (`attachment.video`) plays its clip silently in a loop in streams, sized by the original's arithmetic (`utils/image-region.ts`: fitted to the grid column or the list's content width, never past 1:1), and shows its still on the post page, in comments on a post page and on iOS. A GIF plays from its `optimized` file. Embeds (`embed-region.tsx`) are the original's `EmbedRegion` plus what `embetter` did to it at runtime: the play button swaps in the service's player, only one player plays at a time, and on phones and tablets a player is put in place while its thumbnail is entirely on screen. As in the original a buy link on an embed is not drawn on the published post (its `EmbedRegion` tests `linkUrl.size`, which a string does not have). On purpose: the player iframe carries `allow="autoplay"`, which today's browsers need before a player in another site's frame may start by itself (the original's does not, so there the service's own play button has to be pressed once more); the server sends the still of a video attachment and the clip takes over once the page is live (only the browser knows whether it is iOS); a grid picture keeps its place while it loads (the original has no size for it until it arrives, so its grid jumps).
- **Invites with no submissions:** the original treats the empty API answer as one blank submission and shows only a "Submissions" heading (a bug). The rewrite shows the zero state the original's code intended ("No Submissions Yet"), about 0.4% diff on `/invites/tiny-worlds`.
- **Search with no results:** the original's reducer turns an empty `posts` / `users` array into one blank item (an empty array is an `object`), so it shows an empty grid and no text. The rewrite shows the zero state the original's code intended ("Sorry, no results found."), about 0.1% diff on `/search?terms=zzzz` (Posts and People).
- **After resetting a password:** the original's saga signs in with the username from its (logged out, so empty) store, so nothing visibly happens and the form stays. The rewrite does what the saga meant to: signs in with the new password and goes to `/`. The mock's reset link is in its log and at `GET /mock/last-reset-link`.
- **Onboarding avatar "blank" check:** like the original, an avatar or header only counts as present when the profile says `hasAvatarPresent` / `hasCoverImagePresent` (the mock sets them once you upload one), so seeded users show the green upload buttons here.
- **Category tile order after category posts load:** the original's GraphQL category fragment only requests `id`, `slug` and `name`, but its reducer merges `level` and `order` too (as undefined), so once posts with categories load its tab sort breaks and the tiles fall back to load order. The rewrite keeps the correct order, so the first tiles can swap on feeds that show category headers (about 2% on those pages).
- **Curator feature/unfeature buttons in a post's category history:** ported. The original draws no role logic of its own: `FeatureCategoryPostTool` (`src/components/posts/PostTools.js`) shows a grey badge button for a `submitted` category post when the API sends `actions.feature`, a green `.featured` badge button when it sends `actions.unfeature` on a `featured` one, and the plain badge otherwise; the API decides who gets the actions, so the rewrite requests `categoryPosts { actions { feature unfeature } }` and does the same. The mock makes ada a curator of Art and Design and grace a moderator of Photography (`mock/category-posts.js`, both roles may curate; this is the mock's assumption), with a few submitted and curator-featured posts (on a fresh database e.g. `/yuki/post/p5x6865` submitted, `/yuki/post/p12x9270` featured, both in Art). On a category page the header of a stream post draws the same toggle with the star (`CurateIcon`) next to the age (`CategoryFeatureTool` in `components/lightbox/lightbox-feature-tool.tsx`, used by `PostCard.Header` and `RepostHeader`), and so does the lightbox, see the lightbox entry below.
- **Lightbox:** ported to `components/lightbox/` from `LightBoxContainer`, `PostLightBoxContainer`, `LightBoxRenderables` and the lightbox half of `ImageRegion`. A stream, a submissions stream, the post of a post page and a post's comment list each wrap their content in a provider (`PostsLightbox` / `CommentsLightbox`); pictures below it open the overlay through `useLightbox().toggle(assetId, postId)`. When a click opens it is the original's rule: a static picture (list streams, post pages, comments) opens it anywhere on the picture, a grid picture links to the post and only its round hover button (or the corner-brackets tool in the post tools on touch devices) opens it, ⌘-click never does. The queue is every picture of every loaded post, drawn as a window of six pictures before and five after the selected one; pictures are measured at the size the original's `srcset` gives them and scaled to the padded viewport (`image-scale.ts`), and the queue slides by measuring the DOM like `slideQueue`. Opening from a grid waits 1250ms before the queue shows, like the original. Keys while open (`use-lightbox-keys.ts`, names in `constants/shortcut-keys.ts`): Esc or 5 close, → k ] 6 next, ← j [ 4 previous, l loves the post (signed out it lands on `/enter`, which is where the original's refused request ends up). As in the original the page behind is not scroll-locked but follows the selected picture, and the navbar, footer and Discover category strip are tucked away (`body.isLightBoxActive`). The post tools in the lightbox are the stream's own (`LoveButton`, `RepostTool`, `ShareTool` with an `isLightBox` class); how they look depends on where the original draws the lightbox, because page CSS reaches into it: next to a stream's posts, inside `.Posts.asList` on a post page, and under 60em inside the post page's `.Post` as well, where the page's tool rules apply (no comment tool, larger icons, love and repost at the edges). `lightbox.tsx` gives the overlay the matching classes (`LightboxPlacement`). Loves and watches made in a stream (card or lightbox) are written into the stream's query cache (`components/streams/stream-cache.ts`), otherwise the heart or bolt fell back as soon as the request finished; artist-invite submission streams keep their pages in the query cache the same way (`components/artist-invites/use-submission-pages.ts`). Differences on purpose: the overlay is a `role="dialog"` that takes focus and gives it back; next/previous are worked out from the loaded posts on every render (the original only refreshes them when the selection changes, so right after more posts load its Next needs two presses); the selected picture is re-centred when a picture gets its size after the queue has already moved (the original leaves it off centre on a slow connection). A video attachment plays its clip in the lightbox when it was opened from a stream (not on a post page, not on iOS), sized like a list stream's and then scaled like a picture (`LightboxClip` in `lightbox-image.tsx`). A window resize is handled like the original's (`use-lightbox-sizes.ts`): resize events are debounced (100ms, then a frame), every picture is rescaled once when the viewport really changed, and a resize that ends at the size it started from changes nothing. Three things the original gets wrong are not copied: for comment pictures it means to show the parent post's tools but its GraphQL reducer never sets the comment's `originalPostId`, so it shows a lone eye with "NaN" (the rewrite shows the post's tools, about 0.1% on that state); after the window shrinks it rescales pictures from a measurement taken while `max-width: 100%` squeezes them, which distorts wide neighbours (the rewrite keeps their shape); and with the share dialog open over the lightbox its Esc closes the lightbox underneath and leaves the dialog (here Esc closes the dialog first, as every `Modal` does). On a category page (`/discover/art`...) a curator gets the feature / unfeature star (`CurateIcon`) among the lightbox post tools for posts whose `categoryPosts` entry for that category carries `actions`.
- **Comments in streams:** ported from `PostContainer.onClickToggleComments` and the `Post` renderable. Signed in, a stream post's comment tool (`components/posts/comment-tool.tsx`) opens the comment editor (focused) and the first ten comments under the post and closes them again (`components/comments/stream-comments.tsx`, reusing the post page's `CommentForm`, `CommentList` and `CommentItem`); which posts are open is kept in `stores/stream-comments-store.ts`, like the original's `post.showComments`, so several can be open and they stay open while you move around. From a grid card on a phone (below 40em) the tool goes to the post page instead, and signed out it is a plain link to the post. A post with more than ten comments ends in the grey "See More" pill, a link to the post page (the original never loads a second page in a stream). In a grid the comments' text and pictures link to the post as well, like the post's own. The lightbox's comment tool closes the lightbox and opens the comments under the post (on a phone it goes to the post page); as in the original the bubble only turns black when the post's own tool opened them. The editor's Cancel asks "Cancel comment?" first, in streams and on the post page. After "See More" the post page eases down to the comments like the original's (`use-see-more-scroll.ts`, the port of `scrollToSelector('.TabListStreamContainer', { boundary: 'bottom', offset: 200 })`; it is a window scroll, so nothing moves from 60em up, where the side bar scrolls). An unsent comment is gone once the comments are closed or the page is left, as in the original: its comment editors are not persisted, and `EDITOR.INITIALIZE` empties them every time they mount (only the omnibar's draft is kept). The bubble's lava-lamp loading animation (`isCommentsRequesting`) is not ported because the original never shows it: its selector waits for `LOAD_STREAM_REQUEST` while comments load through `V3.LOAD_STREAM_REQUEST`.
- **Related posts:** ported (`components/post-detail/related-posts.tsx`, `services/related-posts.ts`). Under a post the original loads `GET /api/v2/posts/~token/related?per_page=n` and shows one row under a "Related Posts" title: `n` is the viewport's column count, less one from three columns up, drawn as grid cards (summary, pictures linking to the post) in that many columns, less one from four up (`constants/related-posts.ts`); nothing is drawn when there are none, and it never pages. The rewrite loads the widest row (six) with the page and shows the first `n`, so unlike the original the row follows the window when it is resized. A related card has no age tool, and signed in its comment and repost tools go to that post's page, in the card and in its lightbox. The mock chooses the related posts (`mock/related-posts.js`).
- **Category info panel, curators and moderators:** ported (`components/discover/category-info*`, `category-users*`, `category-role-*`). Who may add or remove a role is the original's rule (`selectHasRoleAssignmentAccess`): staff, or people whose profile lists the category in `links.categories`; the original reads that one list for curators and for moderators alike. A list with nobody in it is not drawn, so it has no add button either (as in the original). Two things differ on purpose: pressing Enter in the add-role dialog with no user highlighted does nothing (the original's form has no submit handler, so the browser reloads the page with the text in the query string), and the user search waits 200ms after the last key (the original builds a new debounced function per key, so every key sends a request). Subscribing works too (`PUT /api/v2/profile/followed_categories` with the whole list, like the original): the button turns grey "Subscribed", the hero and the `/discover/all` cards get their green check, and the category strip lists the subscribed categories instead of the zero state. With the mock, the original also lists as curator / moderator whoever its own notifications mentioned in that role (see `mock/README.md`), which the rewrite does not copy.
- **Community Roles administration on profiles:** ported (`components/profile/user-roles-panel.tsx`, `user-roles-form.tsx`, `user-role-item.tsx`, `role-filter-selector.tsx`, rules in `utils/profile-roles.ts`). People who administer a category (`searchCategories(administered: true)` returns it, loaded by the profile layout) get the form in the panel: pick one of their categories, then a position (a curator may hand out Featured User, a moderator also Curator and Moderator; like the original nothing is offered before a category is chosen), then Add. A role's x asks "Remove @name from Category? Yes No" and is only there for roles the viewer may remove (moderators: any role of their category, curators: its featured users, staff: all). Like the original's store, the panel keeps the list once loaded: a new role goes last, and every role of the category just assigned gets the green "new" dot until the panel closes. Differences left in: "Success!" appears when the role is stored (the original shows it on submit, even if the request then fails; here a failure is a toast), and the category box filters the loaded list instead of asking the API again on each key (same result).
- **Staff:** everything the original does for `isStaff` (`selectIsStaff`, read from the profile) is ported, and the mock has one staff user, `saoirse` (`mock/staff.js`). Staff get the add / remove role buttons on every category page (`canAssignRoles`), the Community Roles button on every profile with all three positions in the form and an x on every role (`isRoleAdministrator`, `roleOptionsFor`, `canRemoveRole`), the delete x on anybody's comment (`selectCommentCanBeDeleted`; `components/ui/staff-context.tsx` carries the flag from the root layout to `CommentList`), and "Analytics" after "Settings" in the avatar menu (`NavbarAnalyticsLink`, also for `isBrand`; it is a plain link to `/manage`, a page of the old Rails app that neither app serves). The original's hidden pencil on a role (`.edit`, `display: none` "until we wire it up") is not rendered. A staff-only announcement preview is red (`isStaffPreview`). Not ported because it is not web: telling the Android wrapper about staff (`ElloAndroidInterface.setIsStaff`).
- **Notifications, details that are easy to miss:** the thumbnail is the first image *or embed* of the summary (`regionItemsForNotifications` collects both): an embed shows its picture with the play button, which takes no clicks there. A post with an animated upload gets its clip instead of the still, as in streams, but the original sizes that clip to a column width notifications never pass, so it is 0x0: the row keeps its 80px column and shows nothing in it (not on iOS, where the still is used). A tab is lit when its own path is open (`TabListLinks`), so `/notifications/all`, where the navbar bolt leads below 60em while another tab was last used in the dropdown, shows everything with no tab lit; an unknown type (`/notifications/bogus`) goes back to `/notifications`.
- **Footer:** the email form asks the availability endpoint like the original (`FooterContainer`): the button unlocks once the text looks like an email (`isValidEmail`), a free address gets the green bubble "Subscribed. See you tomorrow" and the form empties itself after 1666ms, a taken or malformed one the red "That email is invalid" (or the server's "Did you mean ...?"), and typing again takes the bubble away. Nothing is subscribed anywhere, as in the original, which only tracked an analytics event. The original ignores the answer when the focus is neither in the field nor on the button; the rewrite does not check that. "Top" eases the window to the top over a second (quartic in-out, `utils/scroll-to-position.ts`) and winds back the post page's two columns too.
- **Invitations:** sending (or re-sending) does not refresh the list next to the form, as in the original: the new address, and the new order after a Re-Invite, show the next time the page is opened.
- **Collab pill when logged out:** the original never shows it to visitors. Its GraphQL reducer stores the setting as `isCollaboratable` while everything reads `isCollaborateable`, so a profile only has it when the same user also came in through a v2 answer (logged in, the notifications preload usually does that). The rewrite shows Collab to signed-in viewers only; Hire is unaffected. A signed-in viewer whose v2 answers never mentioned that user would see no Collab pill in the original but does here.
- **Settings, "Your Data":** Avatar and Header always read "—", as in the original (its `getOriginalAssetUrl` reads `asset.original.url` off an Immutable map, so the "View original image" link it was written for never shows).
- **Settings, "Blocked users" / "Muted users":** ported (`components/settings/relationship-list.tsx`): the two sections appear while the profile's `blockedCount` / `mutedCount` is above zero and list the people with their Blocked / Muted button, which opens the block dialog.
- **Loading views between pages:** the original switched views the moment a link was clicked and drew that view's loader (`StreamContainer.renderLoading()`, the spinning mark) while its request was out. Here a page is rendered on the server, so the same thing is done in the browser: Next reports the start of a navigation (`instrumentation-client.ts` -> `stores/navigation-store.ts`), and until the page arrives `components/layout/pending-main.tsx` stands in for the main view with the original's loader for that route (`route-loading.ts` says which: `/`, `/following`, `/discover...`, `/invites`, `/notifications...`, `/search`), with the navbar, the category strip and the footer already on the new route (`useShownPath`). Between the tabs of a profile the hero stays and only the stream shows the loader (`pending-profile-stream.tsx`); a search being typed shows it in place of the results (`pending-query.tsx`). Compared with `tools/visual-diff --snap` on a delayed mock (its README has the recipe). Known differences, on purpose: (1) the original keeps everything it has loaded in its store, so going back to a stream it has already shown draws the old posts at once and offers "New Posts"; the rewrite shows the loader again and then the fresh page. (2) A profile, a post or an artist invite opened from a stream shows at once in the original (the record is in its store) with only the stream under it loading; the rewrite has no such record in the browser, so the page that is open stays until the new one is ready. (3) The first load of a URL is rendered on the server, so there is no loader at all, where the original shows its loaders after the bundle starts.
- **Navbar and footer while scrolling:** ported from `ViewportContainer.onScroll` (`components/layout/use-navbar-hidden.ts`): past the first screen both bars slide away when the page is scrolled down and return when it is scrolled up, on hover of their edge, or on a new route.
- **A site that changes while you look at it** (`yarn mock` is live, see `mock/README.md`): like the original, nothing is polled. The red dot is asked for on every change of route, the notifications feed is loaded once when the app starts (so the dropdown opens with its list) and again whenever it is opened, and a stream asks for its first page again each time it is opened: posts it has not shown wait behind "New Posts" in the navbar.
